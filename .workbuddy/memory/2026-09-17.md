# 2026-09-17

## V3.62：新用户分配权限后登录没有任何数据（共用本店数据的云同步走错数据空间）

### 现象与排查
- 用户反馈「新用户已分配权限，但是登录后没有任何数据」。
- **关键排查手法**：云端账号表 `data/admin/accounts-sync.json` 用**内置密钥**
  （`sync.ACCOUNTS_PASSPHRASE = 'appliance-erp-accounts-2026'`，AES-GCM + PBKDF2 150000）
  可**离线解密核对**。Node 里 fetch 该文件 → decrypt → 直接拿到全部账号的
  id/username/ownerId/perms，不用登录用户浏览器就能确认配置是否正确。
- 核对结果：新账号 `pifa`（acct1）`ownerId='admin'`（数据空间正确）、
  权限 2 项 `product_read + data_manage`。**账号与权限都没问题**。
- 云端快照探针：`data/admin/erp-snapshot.json` → 200（老板数据已上传）；
  `data/acct1/erp-snapshot.json` → **404**。

### 根因（三层）
1. **业务数据不在账号表里**：账号表云同步（V3.60/61）只同步登录名/权限/数据空间/密码哈希；
   商品·单据·账本在**各设备本地 IndexedDB**，换设备登录天然为空。
2. **代码缺陷（主因）**：`js/ui/page-mine.js` 的同步配置 key 与快照路径按
   `currentAccount.id` 定位 → 员工（acct1）去找 `data/acct1/erp-snapshot.json`（404），
   而老板的数据在 `data/admin/erp-snapshot.json`（200）→ 员工点「从云端恢复」
   永远报「云端还没有快照」。
3. 快照随行的账户档案写员工自己的 → 会把老板店名/头像覆盖。

### 修复
- `page-mine.js` 新增 `syncAcctId()` = `accounts.dataOwnerId(currentAccount)`，
  替换全部 `loadConfig/saveConfig` 的账号维度（共用→admin，独立→自身 id）。
- 新增 `sharesBossData()` / `isEmptyLedger(ctx)`：`sync-up` 在「共用本店数据 + 本机空账本」时
  **阻断上传**（否则员工一次误点会清空全店云端数据）；非空时二次确认「覆盖全店共享快照」。
- 新增 `syncAccountPublic()`：快照档案取归属账号（老板）。
- 新增 `dataSpaceTip()`：云同步卡片显示「数据空间：共用本店数据（applianceErp_admin）/ 独立」。
- `page-admin.js` 新增 `page.dataSpaceOf(a)` + 账号卡片数据空间徽标；新建账号表单补充说明
  「独立数据空间 = 新账号登录后是一本空账」。

### 踩坑
1. **UMD 引用坑（测试）**：`page-mine.js` 的 IIFE 里 `var ERP = root.ERP || {}`，
   若 `globalThis.ERP` 当时不存在，闭包拿的是对象 A，而随后 `root.ERP = root.ERP || {}`
   又指向新对象 B —— 测试里**先 require 再设 `globalThis.ERP.currentAccount` 会取不到**。
   必须在 require 之前先 `globalThis.ERP = globalThis.ERP || {}`。
2. **`sync-up` 是异步的**：内部先 `flushNow(ctx).then(...)` 再 `syncUp`，
   断言是否发起上传必须 `await sleep(5)` 冲刷微任务，同步断言会误判。
3. **`node --test tests/` 不行**，必须 `node --test tests/*.test.js`（package.json 的 test 脚本口径）。
4. **本仓库没有 `origin/gh-pages` 跟踪引用**：`git fetch origin gh-pages` 只写 FETCH_HEAD，
   要 `git reset --hard <FETCH_HEAD 的 sha>`；且 `git reset --hard FETCH_HEAD` 在该 worktree
   会报「Use '--' to separate paths」——直接用 sha 即可。
5. **gh-pages 静态资源有 CDN 缓存**：推完立刻 curl 仍可能是旧版（实测首次 curl 还是 v90/V3.61），
   约 1–2 分钟后复检才变 v91；加 `?cb=$RANDOM` 可提前穿透。
6. 本地 main 与 origin/main 曾出现「同内容不同 sha」的分叉（浅克隆/grafted 历史所致），
   用 `git rebase --onto origin/main <分叉起点> main` 把新提交挑过去即可，**不要 force-push**。
7. 沙箱里 `grep` 工具对部分文件静默返回空，改用 `/usr/bin/grep` 或 Python 读文件。

### 不改代码的临时解法（用户可直接用）
在新用户**那台设备**上先用 `hawsystem` 登录 → 我的 → 云同步 → 从云端恢复
（老板数据落进该设备的 `applianceErp_admin`）→ 退出 → 用新账号登录，即看到同一本账
（因为二者 `dbNameForAccount` 都是 `applianceErp_admin`）。

## V3.63：本机空账本引导（新用户登录不再是一片空白）

- **为什么还要再补一版**：V3.62 只解决了「员工能拉到本店数据」，没解决「他不知道要去拉」。
  新员工在一台新设备登录，看到的仍是一片空白、完全不知道下一步做什么——
  这才是用户最初反馈「登录后没有任何数据」的真实体感。
- **改动**：
  - `js/core/util.js` 新增 `util.isEmptyLedger(ctxOrData)`（商品/进货/销售/账目全空即为空），
    判空逻辑收敛为单一来源；`page-mine.js` 的空库上传保护改为复用它。
  - `js/ui/page-home.js` 新增 `emptyLedgerGuide(ctx)`，插在 `render()` 的提醒区顶部
    （手机端 `mobileHome` 与电脑端 `desktopHome` 共用同一条 `rem`，一次插入两端生效）。按数据空间分流：
    - 共用本店数据：说明「与老板共用同一本账，但这台设备还没拉到数据」+ 两步操作
      （退出 → 管理总控登录 → 我的 → 云同步 → 从云端恢复 → 退出再用本账号登录）+「去云同步」按钮；
    - 独立数据空间：说明是全新空账本 +「去建档 / 导入」按钮。
    - **未登录（无账号上下文）不显示** —— 关键约束，否则大量用 `newCtx()` 的首页单测会凭空多一张卡片。
- **测试**：新增 `tests/empty-ledger-guide-v363.test.js` 6 项；全量 **820/820** 通过。
- **发布**：main `bca54bb`；回滚基线 `v3.62-baseline` → `ee9e719`（git push 502，改用 `gh api` 建远端 ref）；
  gh-pages `c448035`（259eab9..c448035）；线上校验 sw=v92、page-mine=V3.63、page-home 含 emptyLedgerGuide、
  data 两个文件均 200。

### 新增坑
- **git 通道会间歇性 502**（`CONNECT tunnel failed, response 502`）：**多试几次通常就能过**
  （本次 main 第 1 次失败、第 2 次成功；gh-pages 第 1 次失败、第 2 次成功），持续失败才转 `gh api`。
  **绝不 force-push**。
- 循环重试别写 `git push ... | tail -2 && break`：管道返回的是 `tail` 的退出码（恒 0），会误判成功。
  要用 `if git push >log 2>&1; then ... fi`。
- 用 Python 批量替换测试里形如 `sw.includes("var CACHE = 'appliance-erp-vXX';")` 的断言时，
  转义单引号的写法会**静默不匹配**（文件报告 changed 但实际没换），导致两处断言停在旧版本而全量测试红。
  改完版本号务必 `grep -n "v9[12]" tests/*.test.js` 复核三处断言（ui-mine / perf-v358 / 新测试文件）。
- Bash heredoc 里写 Python 时，**Python 字符串内含三引号会炸**（`SyntaxError: invalid syntax`）。
  大段 Markdown 文本用 `cat >> file <<'EOF'` 直接追加最稳，别绕 Python。

## V3.64：首页横幅「已备份」文案真实性（硬编码假备份时间）

- **怎么发现的**：V3.63 做完后看真机截图，发现首页横幅写着「已备份 · 今天 09:12」，
  而同一屏下方的提醒条写着「你已从未备份」——自相矛盾。
- **根因**：`js/ui/page-home.js` 的 `mobileHome` 与 `desktopHome` **各硬编码了一处**
  `<div class="banner-sub">已备份 · 今天 09:12</div>`。
  真实备份时间其实一直存在 `ctx.data.lastBackupAt`（`page-setting.js` 导出备份时写入、
  清空数据时置空），`backupReminder()` 读的就是真实值 → 二者长期不一致。
  **危害**：会让用户以为数据已有备份而放松警惕，属会引发真实数据风险的显示 Bug。
- **改动**：
  - `js/core/util.js` 新增纯函数 `util.backupLabel(lastISO, todayStr)` → `{backed, text}`：
    无记录 → `尚未备份 · 建议尽快导出一份账本`；当天 → `已备份 · 今天 HH:MM`；
    30 天内 → `已备份 · N 天前`；更早 → `上次备份 · YYYY-MM-DD`。
  - `js/ui/page-home.js` 新增 `bannerBackupText(ctx)` 由 `lastBackupAt` 派生，
    两处 `banner-sub` 统一改用（手机端/电脑端一次改两处）。
- **测试**：新增 `tests/backup-banner-v364.test.js` 8 项，其中一条是**交叉断言**：
  「横幅说已备份」与「提醒条说从未备份」不得同时成立（防回归到自相矛盾）。
- **发布**：main `1d55799`；回滚基线 `v3.63-baseline` → `bca54bb`；
  gh-pages `6e7d783`（c448035..6e7d783 快进）；线上校验 sw=v93、page-mine=V3.64、
  page-home 含 `bannerBackupText` ×3、data 两文件 200。

### 通用教训
- **硬编码的"状态文案"是隐患**：凡是会随数据变化的展示文案（备份时间、同步时间、统计数字），
  必须从真实数据派生。审查手法：在 UI 层/模板里 grep 形如 `今天 09:12`、`¥0`、`0 条`
  这类**写死的示例值**——它们在 demo 里看着正常，上线后就是谎言。
- 改完 UI 后**一定要看真机截图**，不要只跑断言。这个 Bug 全量测试 820 项全绿也没发现，
  因为它不是"渲染错"，而是"渲染了一个假数据"。
